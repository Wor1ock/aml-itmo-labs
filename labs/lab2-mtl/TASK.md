> Рабочая версия ТЗ. Общие требования и матрица применимости — в
> [`../README.md`](../README.md). Это не официальный документ: окончательное решение
> за преподавателем.
>
> Вес: 1.0.

## 1. Что нужно сделать

Взять задачу с несколькими модальностями (удобно переиспользовать лабораторную 1) и
добавить к ней multi-task learning: одна общая часть модели решает несколько задач,
для каждой задачи есть своя голова, лоссы агрегируются. Нужно не просто добавить
вторую голову, а проверить гипотезы:

- помогает ли совместное обучение основной задаче;
- какие вспомогательные задачи помогают, а какие мешают;
- как выбор весов лоссов влияет на результат;
- есть ли negative transfer и в каких задачах.

Работа должна показать понимание MTL как идеи, а не как «две головы и сумма лоссов».
Конкретные метрики не важны; важны корректная постановка, baseline и честный анализ.

## 2. Чему должна научить работа

- понимать MTL как паттерн: общее представление + специфичные для задач части;
- понимать, что MTL может быть регуляризацией, но это зависит от роли, а не от названия;
- видеть разницу между «несколько задач» и «несколько выходов одной задачи»;
- уметь анализировать связанность задач и negative transfer;
- уметь балансировать лоссы и объяснять выбранный способ;
- измерять эффект MTL по каждой задаче, а не только по среднему.

## 3. Задача и данные

### 3.1. Базовая траектория: лабораторная 1 + вспомогательные задачи

Рекомендуется взять датасет и fusion-модель из лабораторной 1 и добавить задачи,
для которых уже есть разметка. Примеры:

- IEMOCAP/MELD: основная задача — эмоция (4–7 классов); вспомогательные — сентимент
  (3 класса), VAD-регрессия (valence, arousal, dominance), пол диктора;
- FSC: основная задача — интент; вспомогательные — `action`, `object`, `location`
  как отдельные головы, при наличии — диктор; слоты сильно коррелируют, это нужно
  явно обсудить;
- e-commerce: категория товара + ценовой сегмент/бренд/рейтинг;
- NLP/табличные данные: основная классификация + вспомогательная регрессия/NER/тон;
- своя многозадачная задача с двумя и более разными метками.

Требования к задачам:

- минимум две задачи: одна основная и хотя бы одна вспомогательная;
- задачи действительно разные по смыслу и меткам, а не дубликаты одной;
- метки доступны для достаточного числа примеров; если разметка частичная —
  маскировать лосс, а не подставлять нули;
- связанность задач анализируется до обучения: корреляция меток, баланс классов,
  пересечение признаков; высокая корреляция — не запрещена, но должна быть объяснена.

### 3.2. Альтернативы

- Новая многомодальная задача с двумя метками: эмоция + сентимент, интент + диктор,
  категория + атрибут.
- Одномодальная MTL: текст (тональность + тема), аудио (жанр + настроение),
  табличные данные (несколько таргетов).
- MTL с регрессией и классификацией одновременно: например, эмоция + VAD.
- MTL с разными уровнями разметки: сильная метка на подвыборке, слабая на всей.

Главное — не «две головы на одном выходе», а разные задачи, которые могут делить
представление.

### 3.3. Данные и split

- Используется тот же split, что в лабораторной 1, или новый, но без утечек.
- Для дикторов/пациентов/видео — group split или leave-one-speaker-out; один объект
  не должен быть в train и test.
- Если задачи имеют разные подвыборки, split делается по объектам, а не по строкам;
  маски отсутствующих меток сохраняются.
- Тест не используется для выбора весов лоссов, числа эпох или вспомогательных задач.
- EDA: распределение каждой метки, корреляционная матрица, пропуски, пересечение
  подвыборок, примеры, где задачи согласованы/противоречат.

## 4. Метод

### 4.1. Архитектура

Обязательная схема:

1. Общий энкодер (можно переиспользовать fusion из лабораторной 1).
2. Общее представление `h` (после pooling/CLS).
3. Отдельная голова на каждую задачу: `head_i(h) -> logits_i` или `value_i`.
4. Функция потерь: `L = Σ_i w_i * L_i`, где `w_i` — веса; для отсутствующих меток
   `L_i` маскируется.
5. Обратный проход по суммарному лоссу; логирование каждого `L_i` отдельно.

Допустимы task-specific adapters, FiLM или conditional heads, но общая часть должна
быть реально общей и использоваться всеми задачами. Если у каждой задачи свой
полностью независимый энкодер — это не MTL, а ансамбль.

### 4.2. Балансировка лоссов

Нужно реализовать и сравнить минимум два подхода:

- равные веса (например, `w_i = 1`) и/или ручной sweep по одному-двум значениям;
- uncertainty weighting: обучаемые веса/дисперсии, формула вида
  `L = Σ L_i / (2σ_i²) + log σ_i`;
- PCGrad: если градиенты задач конфликтуют (скалярное произведение отрицательное),
  проекция одного градиента на нормальную плоскость другого;
- GradNorm или другой обоснованный метод — по желанию.

Для каждого подхода указать, какие параметры обучаются, как считается градиент и
почему выбран этот вариант. Если используется готовый метод, дать ссылку и объяснить
формулу; одного вызова библиотеки недостаточно.

### 4.3. Baseline

Все сравнения — на одном split и, по возможности, при сопоставимом бюджете:

- single-task модель на каждую задачу отдельно (главный baseline);
- общая часть + только основная голова;
- MTL со всеми задачами;
- MTL с подмножествами задач (leave-one-task-out): все минус одна;
- при возможности — отдельные модели vs одна общая, с числом параметров и временем.

Если MTL не лучше single-task, это нормальный результат. Нужно показать, где именно
он хуже/лучше и почему. Negative transfer — такой же вывод, как и прирост.

### 4.4. Метрики

Для каждой задачи — своя метрика:

- классификация: accuracy, macro-F1, per-class precision/recall/F1, confusion matrix;
  при дисбалансе macro-F1 важнее accuracy;
- регрессия: MAE/RMSE, для affect — CCC (concordance correlation coefficient);
- бинарная/многометочная: F1, AUROC, average precision — по смыслу;
- агрегаты: unweighted/weighted average по задачам, но не вместо per-task таблицы.

Обязательна таблица «задача × метод» с mean ± std/CI. Среднее по задачам без
per-task разбивки не принимается.

### 4.5. Статистика

- Минимум 3 seed (рекомендуется 5) или leave-one-speaker-out по фолдам.
- Для каждого метода — среднее и разброс/CI по seed/фолдам.
- Сравнение с baseline — по разнице метрик, желательно с парным тестом или CI
  разницы; не только «0.81 vs 0.80».
- Если задач несколько, не делать вывод по одной удачной задаче; смотреть на все.
- Проверять, что improvement не вызван утечкой, дисбалансом или подбором веса на тесте.

### 4.6. Анализ MTL

Обязательные артефакты анализа:

- корреляционная матрица меток/задач;
- per-task learning curves (все лоссы и метрики);
- таблица «какие задачи помогли/навредили»;
- gradient conflict: косинусное сходство градиентов задач, хотя бы для нескольких
  шагов/эпох; для PCGrad — как часто проекция срабатывала;
- примеры, где основная и вспомогательная задачи дают разные предсказания;
- ablation: убрать одну задачу, изменить вес, заменить голову;
- вывод о relatedness: какие задачи делят полезные признаки, какие конкурируют.

## 6. Требования

### 6.1. Функциональные

- `docker compose build` и одна команда запускают EDA, обучение, оценку и отчёт.
- Есть smoke-конфиг: маленькая подвыборка, 1–2 эпохи, один seed.
- Есть полный конфиг с фиксированным seed и всеми задачами.
- Инференс возвращает предсказания по всем задачам в понятном виде.
- Если лабораторная 2 переиспользует код лабораторной 1, репозиторий всё равно
  самодостаточен: код лежит внутри или подключён как опубликованный пакет.

### 6.2. Инженерные

- Docker: данные и статическая предобработка на сборке; код последним; read-only
  данные, writable outputs; `.dockerignore`.
- Зависимости зафиксированы; версия Python зафиксирована.
- Типизация: публичные функции, `mypy`, размерности тензоров.
- Конфиг: один источник; CLI > файл > дефолты; без гиперпараметров в env.
- Логирование: логгер, а не `print`; отдельные логи по задачам.
- Тесты: агрегация лоссов, маски, формы голов, gradient flow, интеграционный smoke.
- Нет Jupyter как финального артефакта.

### 6.3. Отчёт

Отчёт должен содержать:

1. постановку задач и связь с лабораторной 1;
2. данные, split, EDA, корреляции;
3. архитектуру: общая часть, головы, размерности;
4. лоссы и веса, выбранные стратегии;
5. таблицу «задача × метод» с mean ± std/CI;
6. ablation: какие задачи помогают/мешают;
7. negative transfer и gradient conflict;
8. примеры ошибок и расхождений между задачами;
9. ограничения и отрицательные результаты;
10. команды воспроизведения, железо, версии, время.

### 6.4. Тесты

Минимум:

- `test_losses.py`: агрегация, веса, маски отсутствующих меток;
- `test_heads.py`: формы выхода каждой головы;
- `test_gradients.py`: градиенты текут в общий энкодер; конфликт считается;
- `test_data.py`: split, маски, отсутствие утечек;
- `test_integration.py`: 1 шаг обучения + инференс по всем задачам + отчёт.

## 9. Антипаттерны

- Две головы на одни и те же метки, выданные за MTL.
- Вспомогательная задача, которая содержит основную метку или её утечку.
- Нет общего энкодера: две независимые модели, названные MTL.
- Нет single-task baseline; сравнение только с «до/после».
- Только средняя метрика по задачам; нет per-task таблицы.
- Веса лоссов подобраны на тесте; отчёт об этом молчит.
- Нет анализа relatedness и negative transfer.
- MTL подан как гарантированное улучшение; отрицательный результат спрятан.
- Ноутбук вместо пайплайна; ручное скачивание; абсолютные пути; нет типизации.
- Красивые кривые без CI и без ablation.
